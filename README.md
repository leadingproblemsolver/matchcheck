# MatchCheck: Step 0 workbench

Three-way match for **goods**: purchase order, signed receipt (GRN), invoice. It flags differences for a person to review **before payment**. It never approves, releases or changes anything.

## Use it
- **Workbench:** open `index.html` in any browser (offline, nothing uploaded). Pick a scenario, **Highlight matched fields**, **Run check**, **Export exceptions CSV**. **Use your data** takes pasted JSON or three CSV files (redacted data only).
- **CLI:** `python3 matchcheck.py examples/scenario_a.json --out exceptions.csv` (stdlib only; exit 0 = ran, 2 = input error). A folder with `po.csv`, `receipts.csv`, `invoices.csv` also works; `--all` includes clear lines.
- **Tests:** `python3 -m unittest discover -s tests -v` (parity tests need `node`). **Benchmark:** `python3 bench.py`.

## Rules the engine enforces
| Rule | How |
|---|---|
| LC10 no authority | Only `CLEAR_FOR_REVIEW`, `NEEDS_HUMAN`, `HOLD`. There is no approved/paid state (fuzzed in tests). |
| LC11 exact maths | Decimal (Python) / scaled BigInt (browser). No floats. |
| LC12 text is data | description, notes, memo are never read by decision logic. Test injects override text and asserts identical output. |
| LC15 repeatable | Same input in any row order gives byte-identical CSV. Split invoices draw down one cumulative receipt ledger. Reformatted duplicates (`INV-2026-089` vs `INV/2026/0089`) share an operation key. |
| LC25 wording | Money is "indicative review value": not a confirmed loss, not recoverable cash. The UI never says goods are "missing". |

Status meaning: **HOLD** = figures disagree before payment (beyond signed receipt or PO, price over 1%, item not on PO, duplicate). **NEEDS_HUMAN** = evidence incomplete or ambiguous (no signed receipt, blank/unreadable field, price below tolerance, credit note, more than 6 signed receipts on one line, unreadable receipt row).

## Evidence (run 2026-11-01)
- 27 tests pass: scenarios A-E, invariants above, price-tolerance boundary, receipt cap, CLI exit codes and byte-identical CSV.
- **Parity:** the JS engine inside `index.html` and `matchcheck.py` produce byte-identical CSV on all five scenarios, a hostile-values batch, and 1,000 / 5,000-line synthetic batches.
- **Scaling (`bench.py`, this container):** hash operations are linear, about 3 per line (1k: 2,988; 400k: 1,195,932) against 1,988,000 and 318,372,800,000 nested-loop comparisons. Wall time was 20 ms at 1k lines and 20.4 s at 400k. Per-line time rises from 20 to 51 us because of the deterministic sort (O(n log n)) and Python allocation, so it is near-linear, not constant per line. Browser stress button: 1,000 lines in about 9 ms in one headless Chromium run; it reports its own measured time every run.
- UI driven in Chromium at 1440x900 and 390 px wide: no JS errors, no horizontal scroll on mobile, nothing evaluated before Run check, data containing HTML is shown as text.

## Not done / not proven
- **No OCR or PDF reading.** Soft copies must be normalised to the JSON/CSV columns first (see `examples/`).
- **No public dataset benchmark yet** (BPI Challenge 2019, SROIE etc. were not downloaded or run here). Synthetic data is generated by `synth()`.
- Partial delivery uses a cumulative sum per (PO, item); there is no subset-sum search. More than 6 signed receipts on a line goes to a person rather than being attributed.
- Single currency (QAR label), exact-match item codes, one price tolerance (1%). No real customer data has been run.
- The original prototype zip was not available in this environment, so this is a fresh build. Align it with the prototype's engine before treating either as canonical.
